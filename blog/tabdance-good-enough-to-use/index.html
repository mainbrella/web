Getting a signed macOS DMG release working with free GitHub Actions

October 10, 2026 · Andrew Arrow

I wanted people to try TabDance, the macOS terminal I’m building, without installing Xcode. The build ran on a free GitHub Actions Mac runner, and my Developer ID certificate imported successfully. Then the packaging step failed:

…: no identity found

The build machines are free for public repositories like TabDance. The signing certificate requires Apple Developer Program membership, usually $99 USD a year.

Workspaces on the left

I want workspaces down the left side of my terminal, like cmux has. Each project gets a place for its tabs, instead of leaving me to remember which window belongs to which project. That’s the reason I wanted another terminal app.

I tried bringing that layout to a Rio fork. It gave me the workspace drawer I wanted, but as I kept using it, clearing, copying, pasting, and typing still felt different from Apple Terminal.

For example, I clear with Command-K, run cat file.txt, then press Command-A to copy the contents. I expect the old build log to be gone. Clearing while editing a long command should preserve the whole wrapped command. Those differences are why I moved on from Rio and started inspecting Apple Terminal’s executable. The first post covers that work.

TabDance is the next attempt: a native Swift and AppKit app using SwiftTerm for terminal emulation and rendering. It has the workspace sidebar and live tabs, with shells that keep running when I switch projects. Command-K preserves the command being edited; a selection keeps a text snapshot for copying after a redraw.

Start with the app bundle

The workflow uses macos-latest, checks that the runner is arm64, runs the tests, then builds for Apple silicon:

xcodebuild -project TabDance.xcodeproj -scheme TabDance \
  -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath .build/xcode -skipPackagePluginValidation \
  ARCHS=arm64 ONLY_ACTIVE_ARCH=YES test

./build-app.sh ARCHS=arm64 ONLY_ACTIVE_ARCH=NO

The Xcode project is checked in; Swift Package Manager fetches the pinned SwiftTerm dependency. -skipPackagePluginValidation skips interactive approval for its build-information plugin. The build script puts the Release bundle at dist/TabDance.app.

That bundle has an ad-hoc signature. It can pass a signature-integrity check without identifying an Apple-registered developer. For distribution outside the App Store, this workflow uses a Developer ID Application certificate.

The certificate was there

The runner needs both the certificate and its private key. Export them together from Keychain Access as a password-protected .p12 archive, then add two repository secrets under Settings → Secrets and variables → Actions:

Required secrets for Developer ID signing
SecretValue
MACOS_DEVELOPER_ID_P12The base64-encoded certificate and private-key archive.
MACOS_DEVELOPER_ID_P12_PASSWORDThe password used to export it.

On a Mac, base64 -i DeveloperID.p12 | pbcopy puts the encoded archive on the clipboard. The workflow decodes it into a temporary file. The keychain gets its own random password, separate from the archive’s export password. Here’s the import, with those temporary paths and the keychain password already set:

security create-keychain -p "$keychain_password" "$keychain_path"
security unlock-keychain -p "$keychain_password" "$keychain_path"
security import "$certificate_path" -k "$keychain_path" \
  -P "$MACOS_DEVELOPER_ID_P12_PASSWORD" -T /usr/bin/codesign
security set-key-partition-list -S apple-tool:,apple: -s \
  -k "$keychain_password" "$keychain_path"

The last command allows Apple’s signing tools to use the private key without a GUI prompt. An unlocked keychain alone doesn’t grant that access.

In the failed signing run, that setup succeeded. The identity check explicitly queried the temporary keychain and found the Developer ID identity. Packaging still failed with the error at the top of this post.

The fix added the temporary keychain to the runner’s user keychain search list. These are the relevant lines, with the code that parses the saved list omitted:

# This check queries the temporary keychain directly.
security find-identity -v -p codesigning "$keychain_path"

# Add it to the saved user search list before signing.
keychain_search_list+=("$keychain_path")
security list-keychains -d user -s "${keychain_search_list[@]}"

We were already passing --keychain to codesign. Its entry in man codesign distinguishes two lookups: that option selects where to find the signing identity, while assembling the certificate chain still uses the user’s keychain search list. Naming the keychain in one command hadn’t made it available to every lookup.

Adding the search-list entry got signing past that failure. The workflow selects exactly one valid Developer ID Application identity and passes its SHA-1 hash to the packaging script, avoiding ambiguity between certificate names.

Cleanup restores the original search list and deletes the temporary keychain under if: always(). A follow-up fix handles unset variables and an empty original list: with set -u, cleanup has to work even when setup didn’t finish.

Sign the app, then the disk image

The DMG contains the signed app and a symlink to /Applications. Finder resolves that link into the familiar drag-to-Applications destination. Here are the packaging steps, with verification and optional notarization omitted:

codesign --force --options runtime --timestamp \
  --sign "$MACOS_SIGNING_IDENTITY" \
  --keychain "$MACOS_SIGNING_KEYCHAIN" dist/TabDance.app

staging="$RUNNER_TEMP/tabdance-dmg"
mkdir -p "$staging"
ditto dist/TabDance.app "$staging/TabDance.app"
ln -s /Applications "$staging/Applications"
hdiutil create -volname TabDance -srcfolder "$staging" \
  -ov -format UDZO dist/TabDance-macos-arm64.dmg

codesign --force --timestamp --sign "$MACOS_SIGNING_IDENTITY" \
  --keychain "$MACOS_SIGNING_KEYCHAIN" \
  dist/TabDance-macos-arm64.dmg

--options runtime enables the app’s hardened runtime; --timestamp requests a secure timestamp. UDZO makes a compressed, read-only image. The full script clears old staging output first and verifies both signatures after signing.

Pull requests build ad-hoc signed artifacts without importing the certificate. Published builds require the signing secrets, and the publish job refuses an artifact unless the packaging job reports Developer ID signed.

The DMG still wasn’t on Releases

actions/upload-artifact stores the DMG under the workflow run, where this workflow keeps it for seven days. It doesn’t attach the file to a release. GitHub’s automatic source ZIP and tarball don’t contain the compiled app either.

A second job waits for the Mac build, downloads that same DMG, and publishes it from Ubuntu. Its contents: write permission and GH_TOKEN set to ${{ github.token }} let the GitHub CLI create a release. GH_REPO identifies the repository. The upload’s core is:

TAG_NAME="${COMMIT_SHA:0:8}"
sha256sum TabDance-macos-arm64.dmg > SHA256SUMS
gh release create "$TAG_NAME" \
  TabDance-macos-arm64.dmg SHA256SUMS \
  --title "$TAG_NAME" --target "$COMMIT_SHA" --generate-notes

The tag names the commit that was built, and --target points the new tag there. Reruns update the existing release with gh release upload --clobber. The same short SHA appears in About TabDance, so an installed binary can be matched to its source.

One upload still returned 403 even though the job log showed Contents: write. A newer workflow fix had reached main while that older build was running. This matches a release API restriction: when the target commit changes workflow files relative to the current default branch, release creation also needs Workflows write permission. The built-in GITHUB_TOKEN can’t have it.

Publishing arbitrary older commits therefore needs a suitably authorized GitHub App or token. The successful run used the built-in token and produced release 47710798, with the signed DMG and its checksum attached.

Signed, with notarization still to do

The release says Notarized: false. Signing identifies the developer and protects the signed contents. Notarization submits the software to Apple for automated checks; stapling attaches the resulting ticket so Gatekeeper can find it offline.

The optional path in our script uses an App Store Connect API key: a .p8 file, key ID, and issuer ID. These authenticate the submission; the .p12 supplies the signing identity. The script notarizes and staples the app before copying it into the DMG, then submits and staples the signed DMG too:

xcrun notarytool submit "$dmg" \
  --key "$notary_key" --key-id "$APPLE_NOTARY_KEY_ID" \
  --issuer "$APPLE_NOTARY_ISSUER_ID" --wait --timeout 30m
xcrun stapler staple "$dmg"
xcrun stapler validate "$dmg"

That path is implemented; the linked release didn’t run it. Its Developer ID signature doesn’t promise a first launch without a Gatekeeper warning.

On an Apple silicon Mac running macOS 13 or later, download TabDance-macos-arm64.dmg from the release and drag the app to Applications. If macOS blocks it, Apple documents Open Anyway under System Settings → Privacy & Security. The README covers building from source, including for Intel Macs.
