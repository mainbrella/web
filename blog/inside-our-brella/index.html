inside-our-brella

October 7, 2026 · Mainbrella Engineering

A request to create a machine times out. The machine may already be running. Retrying could start a second one; doing nothing could strand the first. Now suppose the original machine stops, its slot gets reused, and a delayed cleanup request finally arrives. It must leave the replacement alone.

This is the problem that connects much of Mainbrella’s backend. The HTTP API lets a caller create Linux machines, run commands, transfer files, connect private services, and save workspaces. Beneath those operations, the code keeps track of which request reserved the work, which incarnation of a machine owns it, and what survived an interrupted response.

The answer starts with three distinct identities: an idempotency key for an operation, an internal reservation number for admission, and a returned (id, createdAt) pair for a running machine. Following those identities through the backend source explains both the useful guarantees and the places where recovery stops.

The API, the account, and the machine

The public API Worker first resolves the caller. A named API key and a browser session can both lead to the same user ID. An explicit invalid bearer credential fails authentication; it does not fall back to a valid browser cookie. For creation, the handler also resolves billing and translates a catalog ID or an owned, ready custom image into a server-selected runtime image. The client does not choose an arbitrary private image key. These decisions live in the container handler and container authentication.

The handler then addresses a ContainerAccount Durable Object by account:${userId}. A Durable Object here is an addressable coordinator with durable storage: later requests for that account reach the same logical owner, including after its JavaScript instance is reconstructed. That owner stores the occupied slots, monthly starts, reserved compute, creation receipts, and workspace index. The private service registry lives in the same account object, with its own controller and serialization queue.

Each slot has a separate UserContainer Durable Object, reached through a name derived from the account and slot. Its controller owns the current generation, deadlines, and the platform container handle. It also composes the command, file, execution, preview, and private-service handlers. The Linux guest is where application code runs; it is not the authority on account allowance or routing identity. See the account wrapper and the runtime wrapper.

This division matters during a burst. Two guests cannot independently decide that the account has one remaining slot. The decision belongs to their shared account coordinator. Once admission is recorded, their separate runtime objects can boot in parallel.

Reserve first, then release the lock and boot

In container-account-core.js, serialized() is a promise queue. Each caller waits for the previous operation and releases the next in a finally block. The create path uses that queue to reconcile existing machines, check allowance, and reserve a slot. It deliberately leaves the queue before waiting for the new machine to boot.

Admission checks four different constraints: the number of occupied slots, the sum of their concurrent compute units, the monthly start count, and remaining compute time. A free slot does not imply enough compute allowance. Conversely, unused monthly compute does not imply that another machine fits the concurrent limit.

For an admitted request, the account increments the monthly start count, records the slot as occupied and pending, reserves runtime, and allocates an increasing reservationId. If the caller supplied an Idempotency-Key, it also writes a creation receipt containing the request fingerprint, slot, reservation number, and a 24-hour expiry. The consequential write is small:

// From container-account-core.js, inside serialized admission.
await this.ctx.storage.put({
  [KEY]: state,
  [CREATION_PREFIX + idempotencyKey]: creation
});

The multi-key put commits the account state and keyed receipt atomically. A failure cannot leave a recorded creation key without its charged reservation, or charge that reservation without its key. Boot starts after this write. Pending slots count toward capacity, so another request cannot claim the same space while readiness is unresolved.

After boot, the original request reenters the queue and rereads account state. It checks that the slot still belongs to its reservation before clearing the pending marker. That last check prevents an old boot response from erasing the bookkeeping for a replacement created while it was waiting.

There is a cost to this scheme: reconciliation and some feature preflights still run within account admission. Moving boot outside the queue removes the readiness wait from that critical section; it does not make all account operations independent or establish any particular launch throughput.

A missing response leaves a reservation, not a blank slate

A matching keyed retry finds the existing receipt before trying to reserve another slot. The same key with different creation inputs returns idempotency_key_conflict. A matching receipt is checked against the current reservation: if that operation’s machine is gone, the reply reports creation_no_longer_running rather than returning whatever now occupies the slot.

An unresolved reservation is initially reported as starting. For the first 90 seconds, reconciliation retains its pending state. After that interval, the account asks the runtime what actually exists. If a machine is running, the account recovers it. If the runtime looks empty, the account sends a fenced stop before releasing the slot, closing the path by which a delayed boot could arrive after the slot was declared free. An unreadable runtime keeps its reservation and capacity; uncertainty does not become permission to launch another machine.

The provisional createdAt on a starting entry comes from the pending timestamp. The runtime chooses the authoritative generation when it starts. A client should retain the identity from the running result before using generation-bound operations.

A successful reservation consumes a start even if boot subsequently fails. Confirmed stop can release unused compute time; it does not refund the start. These are different ledgers. The account tests exercise a machine whose boot response is lost, concurrent keyed retries, delayed dispatch, slot reuse, and a late response crossing a replacement reservation. They test the recovery mechanism directly rather than treating an HTTP 503 as proof that no work happened.

A slot name is an address. A generation is an incarnation.

Slots are reusable: the legacy first slot is named small, followed by c1, c2, and so on. The first slot’s name is historical; it does not mean that its machine size is Small. A delayed operation addressed only to c17 cannot tell whether it is reaching the machine it originally meant.

Running machines therefore return both a slot ID and a generation timestamp. In user-container-core.js, generation allocation is:

const createdAt = Math.max(
  now,
  (previousMetadata?.createdAt ?? -1) + 1
);

The timestamp increases within the slot even when recreation happens in the same millisecond or the wall clock moves backward. Its important property is uniqueness for that slot, not perfect correspondence to a physical clock reading. Command launch, file access, private service registration, and terminal activity check the exact generation against stored metadata.

That protects work after a machine exists. The internal reservation number protects the earlier gap, when a boot has been admitted but may not have reached the runtime. The runtime persists the highest accepted and canceled reservations. A delayed start at or below that fence is rejected. A stop for a reservation older than the accepted replacement returns status without stopping the replacement.

These checks sit at different boundaries for a reason. An account may have approved work before a stop or billing change. By the time a process is about to start, the runtime checks its own current generation and paid lease again, under its lifecycle queue. Admission at an earlier boundary is not a permanent authorization.

Compute allowance becomes a deadline

The account reserves compute in unit-milliseconds. Machine sizes have fixed weights: Lite uses one compute unit; XL uses 28. For a proposed size, remaining allowance translates into the longest affordable duration. The initial end time is the earliest of:

start + plan maximum session duration
paid entitlement expiry
next UTC month boundary
start + floor(remaining unit-ms / machine compute units)

This is a rendering of the calculation in the account controller, not a billing measurement. As an arithmetic example, 60 unit-minutes could reserve a one-unit machine for an hour or a six-unit machine for ten minutes, before the other deadlines shorten either session. The account commits that reservation before boot, so concurrent creates cannot each spend the same remaining allowance.

On a confirmed stop, settleLease() keeps elapsed time and releases the unused portion once. If the machine cannot be read or stopped, its reservation remains. This conservative accounting can temporarily make allowance unavailable during a failure, but it prevents an unconfirmed stop from creating spendable time.

The runtime also has an idle deadline. Useful activity can move that deadline forward; it cannot move the hard deadline. Status polling does not count as activity. Stored absolute deadlines survive controller reconstruction, and request handling checks expiry even when an alarm has not yet run. A plan change can shorten an existing lease; it cannot extend the original hard end.

Paid entitlement observations carry a checkedAt value. Both account and machine retain a newer observation over an older one; an unpaid decision wins a tie. This prevents an old paid request from reinstating access after a newer revocation. It does not turn a cached billing observation into instantaneous knowledge of every external change. The ordering rule and the deadline are explicit in the runtime controller.

The process can outlive its HTTP connection

Foreground execution ties a short command to a request and caps its timeout at 60 seconds. Managed execution separates admission, observation, and cancellation. POST /containers/executions requires an idempotency key, persists an execution record, and returns HTTP 202. A later request can retrieve results, stream output, supply enabled stdin, or cancel that execution.

In executions.js, the durable record exists before the process starts. It stores the execution ID, machine generation, key, fingerprint, status, and output cursor. The fingerprint hashes the execution options, including arguments, timeout, working directory, and sorted environment entries. Raw command and environment values are not retained in that record, although an application can of course print them into retained output.

Retries with the same key, generation, and fingerprint recover the same execution. They do not rerun its command. The controller retains up to 32 execution records per slot, with a one-hour retention deadline measured from admission. If all retained identities are still live, another admission is rejected rather than evicting a key whose caller might retry.

Output events get monotonically increasing sequence numbers. Each event and its updated record cursor are committed together. An SSE client reconnects with its last processed cursor; the stream reads events after that sequence. The implementation’s stream sessions last up to 30 seconds, so reconnecting is part of normal observation. Closing a stream detaches the observer. Explicit cancellation or a deadline controls the job.

The resource limits are concrete. Foreground commands, managed commands, and file operations share a four-operation pool. Managed timeout is at most 15 minutes and is also bounded by the machine’s hard expiry. Output is limited to 1 MiB across stdout and stderr, and the 512-event bound can stop a very chatty job before it reaches that byte limit. Those limits come from the command contract and the execution contract.

The less convenient case is runtime reconstruction. Stored records survive; JavaScript process handles do not. Recovery marks unfinished executions interrupted and destroys a still-running machine if its generation matches the interrupted work. It does not replay the command. A command could have sent an email or committed a database write before the runtime lost its handle. A durable job ID cannot prove that repeating those effects is safe.

Cancellation also has a boundary. The process supervisor wraps work in GNU timeout and signals its process group so ordinary child processes terminate with the command. A guest process can deliberately escape that group. This is not a per-job cgroup; the machine lease remains the enclosing lifetime boundary.

What actually happens at api.internal

Suppose a caller-only machine and a machine serving HTTP on port 8080 belong to the same private network. The service is registered as api. From the caller, fetch('http://api.internal/users') reaches that service without a public preview or a Mainbrella API key inside the guest.

The name looks like ordinary DNS, but this implementation uses the platform’s outbound HTTP interceptor for *.internal. private-services-runtime.js installs a Worker entrypoint with props containing the caller’s user ID, slot, and generation. The relay removes reserved identity and forwarding headers from the guest request, then supplies those trusted values. A guest-written x-mainbrella-user header does not choose the account.

In PrivateServicesController.route(), the account registry finds the source’s exact generation, its network, and a member named api with a registered port. The destination runtime checks its own live generation and matching registration under its lifecycle queue before opening that port. Service names are scoped to the source’s network, so another network can also have an api.

The potentially slow application response is awaited outside the lifecycle queue. Holding the queue while the application runs would prevent stop or replacement from making progress. Once the bounded response is buffered, the destination checks its generation and registration again, renews activity, and constructs the response under the queue. The account then checks source liveness and rereads membership before releasing it.

This handles an awkward race: a service admits a request, then is detached or replaced while its application is still responding. A single lookup at the beginning would miss that change. The later checks deny response release. They provide no transaction around the application itself; a write performed before detachment stays a write.

The current feature is a deployment-gated private HTTP prototype. It accepts plain HTTP at the default port, forwards to a registered application port, bounds request and response bodies to 1 MiB, and applies a ten-second request timeout. It does not provide arbitrary TCP, HTTPS, or WebSocket transport. The caller must check networking.privateServices in GET /capabilities. Local routing tests are evidence for this path, not proof of production network qualification.

A file path stays an argument

The file API transfers bytes rather than putting an artifact into command stdout. files.js runs a small shell program, but the requested path is passed as a positional argument. A filename containing quotes, a newline, or shell metacharacters remains a filename. The script uses "$1"; it never splices that path into executable shell text.

For a write, it rejects a symlink target, requires an existing parent directory, creates a temporary file in that directory, streams input into it, copies the previous regular file’s permissions when replacing one, and renames it over the target. The final rename is the atomic replacement point. Reads may follow symlinks within the owned guest. This is a transfer interface to that guest’s filesystem, not a separate filesystem isolation boundary.

Transfers are limited to 1 MiB and 30 seconds, within the machine lease, and consume the shared operation pool. Generation and paid access are checked during admission and again at process launch. That second check matters if the machine changes between receiving bytes and starting the file command. A lost write response can still mean the replacement occurred; there is no historical receipt that lets the file endpoint report that earlier write as a retained operation.

Save has two durable commits before stop

A workspace save combines account quota, a runtime snapshot call, and optional machine teardown. In workspaces.js, the account first reserves save capacity and capture budget and persists the operation identity. The runtime then records a capture receipt before asking the provider to snapshot. Once a handle comes back, the runtime persists it, and the account validates and persists its own copy. Only then does stop: true stop the source.

There are two distinct lost-response cases. If the runtime saved the handle but its reply to the account disappeared, a retry can recover that receipt without taking another snapshot. If the provider may have accepted capture but the runtime never saved a handle, the receipt remains ambiguous. A retry refuses to capture again for that workspace ID. The first case is recoverable; the second is deliberately unresolved.

The account holds its serialization queue across the save path, unlike creation’s parallel boot phase. This coordinates save with account start and stop decisions, at the cost of a snapshot delaying other account lifecycle operations. The source runtime also holds its lifecycle queue during capture. Neither queue makes arbitrary guest writes a consistent application checkpoint: an application still needs to quiesce writers or persist progress in a recoverable format.

Restore enters the ordinary creation path with a workspaceId and a fresh creation key. It consumes a start and returns a new generation. The saved image digest must match the deployed runtime image, and size and internet policy must match the workspace. A failed restore does not silently fall back to an empty image.

The snapshot preserves filesystem state. It does not resume RAM, processes, preview configuration, or private service membership. A restored service must start its process and register its new identity. The old registration cannot become valid merely because the files resemble the old machine.

If a managed command writes to a remote database and recovery later reports interrupted, its execution record cannot tell the caller whether the database committed the write. Reusing the execution key recovers the interrupted identity; running the command on a replacement machine is new work. To make that repeat safe, the application needs a stable operation ID and a completion record at the destination. The next fact to recover is the database’s receipt for that operation.
