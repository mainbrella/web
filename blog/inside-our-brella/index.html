When the machine boots but the reply disappears

October 7, 2026 · Mainbrella Engineering

You ask Mainbrella to start a Linux machine. It boots, but the reply never reaches you. Do you retry, and risk starting a second machine?

We save a receipt before booting so a retry can find the first attempt. As we run commands and save disks, the harder question is what that receipt proves: that we tried, or that we have a result we can recover.

Let’s follow a Python job that reads data from another container and writes metrics.csv. We’ll call its script analysis.py and its machine slot c17. Those are examples; the machinery below comes from our open-source backend.

Reserve the slot before booting

Suppose two requests arrive and the account has one slot left. If both read “one available,” boot a machine, and update the counter afterward, both can win. We’ve already spent the money by the time we notice.

Each account gets a Cloudflare Durable Object, a coordinator with persistent storage. It decides which requests get a slot, a monthly start, and compute allowance. Each slot has a separate runtime controller that looks after its machine.

The coordinator handles those decisions one at a time. It saves the reservation before asking the runtime to boot, so the next request sees the slot as taken. The queue in container-account-core.js is explicit: even if a decision pauses at an await, the next one waits its turn.

We release that lock as soon as the reservation is saved. Holding it until Linux was ready would make every machine wait for the previous one to boot. The decisions need an order; the boots can overlap.

One test makes this visible. It sends six requests to a Builder account with five slots, then holds all readiness checks behind a gate. Five machines start booting before we open the gate. The sixth request gets a conflict, and the account records five starts. Both the exclusion and the parallelism matter.

Authentication tells us which account to coordinate. An API key or login session establishes ownership; a caller-supplied x-mainbrella-user header doesn’t. The auth adapter and internal request builder enforce that before coordination starts.

Write the receipt first

Our client sends an Idempotency-Key with POST /containers. Think of it as a receipt number for one attempt: repeating that number asks about the same machine. Changing the image, size, or other recorded configuration while keeping the key gets a conflict.

✗ A new key on every retry

  1. Send a create request with key A. The machine boots; the reply is lost.
  2. Retry the same configuration with key B.

Key B asks for a new start. If capacity allows, you now have two machines.

✓ Keep the key for the original attempt

  1. Send a create request with key A. The machine boots; the reply is lost.
  2. Retry the same configuration with key A.

The saved receipt points back to the original start. No second boot.

That only works if we save the receipt before asking the machine to boot. The account prepares the slot reservation and a receipt containing its reservation number and configuration fingerprint, then commits them together. The essential write in container-account-core.js is:

await this.ctx.storage.put({
  [KEY]: state,
  [CREATION_PREFIX + idempotencyKey]:
    creation,
});

The reservation and receipt land in one atomic write. Otherwise we could charge for a slot without leaving the retry anything to find, or issue a receipt for a slot we never reserved. Booting comes afterward.

Now drop the reply. A retry with the same key finds that receipt instead of reserving another start. It may report starting during the ninety-second pending window. After that, the coordinator checks the runtime. If the machine is running, it returns that machine. It never sends a second boot for the uncertain attempt.

Receipts last twenty-four hours. If the machine has stopped or its slot has been reused, the retained key returns creation_no_longer_running. To ask for a replacement, use a new key. Save the original key and request before sending them; a receipt you’ve lost is hard to look up.

“Running” has a modest definition here. The runtime boots the selected image with sleep infinity, then gives uname -a sixty seconds to succeed. That proves the guest can execute a command. Our Python job still needs its dependencies and its own checks.

An old request meets a new machine

What if the boot request itself is delayed? We cancel its reservation, release c17, and use the slot for a new machine. Then the old request arrives. It has the right slot name and the wrong lifetime.

We number each admitted start. The runtime remembers the newest start it accepted and the newest cancellation. A boot whose number is no newer than either gets rejected. Cancellation saves its number even if there’s no guest to destroy, so a late boot can’t bring canceled work back.

Cleanup needs the same care. A delayed “stop 41” must leave machine 42 alone. The runtime’s DELETE path records the cancellation but won’t destroy a newer guest. Likewise, the account won’t let an old successful boot reply clear the replacement’s pending reservation.

Public commands and file requests use { id, createdAt } to identify the running machine. The slot ID can be reused; that pair identifies a particular lifetime. We compute createdAt as max(now, previousCreatedAt + 1), so two creations in one millisecond—or a clock moving backward—still get different identities.

Keep both values when the machine starts. “Clean up c17” is ambiguous after reuse. Our tests stop and reuse a slot before releasing its old boot request, without even advancing the clock. A successful hello-world launch wouldn’t catch that.

Reserve compute, too

A free slot doesn’t mean unlimited runtime. If several machines can each spend the account’s remaining compute allowance, a counter checked only at launch will let them spend it several times. We reserve their runtime up front.

The size weights in plan-policy.js are one compute unit for Lite, ten for Medium, and twenty-eight for XL. Here’s what happens when a Medium machine stops early:

If we can’t contact the machine, its reservation stays put: it may still be spending that allowance. An admitted launch that fails still uses a monthly start; settling its runtime is a separate calculation.

Internally we track compute-unit-milliseconds. A machine’s hard deadline is the earliest of:

  • The end of its plan’s session limit.
  • Paid access expiration.
  • The next UTC month boundary.
  • The time its reserved compute runs out.

The runtime also has an idle deadline. Actual work can push that deadline back, up to the hard deadline; status polling can’t. A Durable Object alarm stops expired machines after the client has gone away. A plan change can shorten an existing lease, but can’t extend its original hard deadline.

You should still be able to stop a machine when the billing lookup is down. DELETE checks ownership without requiring a fresh billing resolution, and cleanup can use a saved entitlement while it remains valid. We also keep the newest entitlement observation, with an unpaid result winning a tie. A delayed paid result mustn’t undo a revocation.

Close the tab. Keep the job.

Now we can run analysis.py. A foreground command gets at most sixty seconds. For longer work, or work whose result we’ll need after a disconnect, we create a managed execution. It gets its own idempotency key; the request also carries the machine’s exact { id, createdAt } pair.

The body of our POST /containers/executions request is small:

{
  "argv": [
    "python3",
    "/workspace/analysis.py"
  ],
  "timeoutMs": 120000
}
Complete authenticated request 
// machine is the exact { id, createdAt } returned for a running guest.
// Persist executionKey and this request before sending them.
const query = new URLSearchParams(machine);
const response = await fetch(`${apiOrigin}/containers/executions?${query}`, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${apiKey}`,
    'Content-Type': 'application/json',
    'Idempotency-Key': executionKey,
  },
  body: JSON.stringify({
    argv: ['python3', '/workspace/analysis.py'],
    timeoutMs: 120_000,
  }),
});
if (!response.ok) throw new Error(`Execution HTTP ${response.status}`);
const execution = await response.json(); // Save execution.id.

argv passes literal arguments without assembling shell text. In executions.js, we save the execution record before starting the process, so a retry can find the same job. Closing the creation request or output stream doesn’t kill it. Explicit cancellation does.

We save output events with increasing sequence numbers. On reconnect, the client sends its last processed sequence as cursor and reads what it missed. Streams last thirty seconds, so reconnecting is expected. The job itself can run for up to fifteen minutes, limited further by its requested timeout and the machine’s remaining lease.

There are limits worth knowing before running an analysis: thirty-two retained execution records per runtime, a one-hour retention period from admission, and four concurrent operations shared with foreground commands and file transfers. Output is capped at one MiB and a finite event count. Reaching the output limit stops the job and marks it truncated. Check the terminal status, exit code, timeout, and truncation before treating its output as a result.

A restarted runtime controller is a different problem from a disconnected viewer. The records survive, but the process handles don’t. Recovery marks unfinished jobs interrupted and destroys their guest if it’s still the current generation. We don’t leave untracked work running or silently rerun the command.

That can cost our Python job an unsaved CSV. It’s still preferable to automatically replaying a command that sends invoices. The caller needs to decide whether the work is safe to repeat.

A service name belongs to a network

Our job reads http://data.internal/shards/west. We register its generation in a private service network, alongside a machine serving as data on port 8080. The caller doesn’t need a listening port of its own.

Which account’s data? Which network? The Python request doesn’t choose. The outbound interceptor in private-services-runtime.js removes reserved identity headers and supplies the account, slot, and generation from the runtime’s configuration. A guest can’t switch customers by inventing a header.

The service registry finds the network containing that source generation and resolves data there. The name can be reused in other accounts and networks. Before opening port 8080, the destination checks that it’s still the registered generation.

It checks again before releasing the response. The account also rechecks the caller and both memberships. Our data service could have been detached or replaced while answering; we don’t want a request authorized under the old arrangement to deliver bytes under the new one. That’s why we buffer the bounded response.

There’s a catch: refusing the response can’t undo a change the application already made. Reading an immutable shard is straightforward. A payment or task-queue service needs its own operation IDs to reconcile a retry.

Rejecting a response doesn’t undo the work that produced it.

This is private HTTP routing, with one-MiB bodies and a ten-second timeout. It doesn’t carry WebSockets or arbitrary TCP: a PostgreSQL client won’t work just because its hostname ends in .internal. Check deployment enablement and GET /capabilities before depending on it.

Take the CSV with you

The job writes /workspace/metrics.csv. While the guest is running, we download it through a generation-bound file request. That endpoint transfers raw bytes, up to one MiB, so we don’t have to squeeze the CSV through a possibly truncated stdout stream.

Uploads in files.js go to a temporary file in the target’s existing parent directory, then rename over the target. A reader sees the old file or the new file rather than half an upload. Paths are positional arguments, never interpolated into shell code. Writes reject symlink targets; reads can follow links inside the owned guest.

We still have to check that the CSV contains the right rows and came from the right inputs. The transfer can’t tell us that. Copy useful output out before destroying the machine. To keep the environment as well, save a workspace.

A saved disk needs a saved address

“Save the disk and stop the machine” sounds like one operation. It involves three parties: the account, the runtime, and the provider doing the capture. None can atomically commit the other two.

The account first reserves save capacity and records the operation. The runtime saves a receipt for that operation, then calls snapshotContainer(). When capture returns, it writes the provider’s handle—the address we need to restore the disk—into that receipt. The account copies the handle into its workspace record. Only then can stop: true destroy the source.

There are two very different places to lose the answer. If the runtime saved the handle but its reply to the account disappeared, a retry reads the receipt and recovers the same capture. If capture was accepted but the runtime controller restarted before saving the handle, the receipt says we tried, with no address to restore from.

workspaces.js refuses to repeat that unresolved capture and returns workspace_save_unavailable. The save path leaves the source intact, still subject to its lease. Trying a new key is a new capture, not recovery of the missing answer.

The quotas reflect that uncertainty. We reserve the source size’s full disk capacity before capture. Deleting a workspace frees its live workspace quota, but doesn’t refund the historical capture budget. The provider may already have done the work; an ambiguous failure can’t be a way to buy unlimited retries.

Restoring a ready workspace goes through normal admission and uses a new start. It gets a fresh generation, keeps the saved size and internet policy, and requires a matching image digest. If the image is incompatible or the provider’s restore fails, we return an error. Substituting an empty machine would make a successful response fairly useless.

A workspace saves the filesystem. It doesn’t save RAM, running processes, previews, or private-service memberships. Our script needs progress in files, and a restored service needs to start and register again. The application also has to quiet its writers before capture. We can faithfully save a disk whose files disagree with each other.

Try the awkward cases

The lifecycle tests let you make these failures happen on demand. From a backend checkout, run:

node --test containers/container-account.test.mjs \
  containers/user-container.test.mjs \
  containers/workspaces.test.mjs \
  containers/private-services.test.mjs

Start with stopping and reusing a slot fences old delayed dispatches even in the same millisecond. It holds a request back until its slot has a new occupant. Then compare lost snapshot response reconciles receipt without recapture with uncertain capture cannot be repeated in the workspace tests. In one case we can retrieve the answer; in the other we have to admit we don’t have it.
